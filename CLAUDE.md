# CLAUDE.md

> This file replaces an earlier version that described a Next.js/Tailwind v3/shadcn/Docker stack
> that was never actually built. Everything below reflects what's really in this repo.

## What this is

A web app for the De La Salle University Chorale: attendance (via an on-screen kiosk, not real
RFID hardware), excuse/paalam requests, fee tracking with an automatic petty-cash escalation
system, event sign-ups, a music library, an announcements board, a rules/guidelines page, a
confidential incident-report system gated behind a separate HR credential, and full admin tooling
for all of the above.

## Where the actual app lives

**`High Fi DLSU Chorale Website/`** — this subfolder is the whole app. The repo root has no
`package.json`; don't run `pnpm`/`npm` commands from the root, `cd` into the subfolder first.
Vercel's project settings point its Root Directory at this subfolder too (see its `vercel.json`).

The "High Fi ..." name and the leftover Figma-Make scaffolding cleaned up in this same commit
(shadcn/ui components, a marketing landing page, Tailwind, MUI, react-router, etc. — see git log)
are because this project was originally generated by Figma Make, an AI Figma-to-code tool. Actual
development since has been entirely hand-written — nothing in the real app uses Tailwind classes
or any of the shadcn/ui primitives; every component is custom-built with inline `style={{}}`
objects and the shared `theme.ts` token set.

## Migrations

`supabase/migrations/*.sql` are plain SQL files with **no CLI/automation** running them. Writing a
migration and pushing it does nothing until it's run manually in the Supabase Dashboard → SQL
Editor. When you add a migration, **tell the user explicitly** that they need to run it (and any
paired `supabase functions deploy <name>` for new/changed Edge Functions) — this has been the
standing workflow all session and there's no reason to assume otherwise.

Migrations are numbered `YYYYMMDD_description.sql` but the numbers don't always match real
calendar dates (this project iterated across sessions faster than the numbering scheme accounts
for) — treat the filename ordering as authoritative for run order, not the literal date.
**Ground truth is whatever's actually in Supabase**, not any single migration file — if a column's
existence matters, check the most recent migration that touches that table before assuming.

## Auth model — the one thing to understand before touching anything security-related

There is **no Supabase Auth JWT anywhere**. Login is: school ID + DLSU email looked up in
`directory`, then a bcrypt password check against `profiles.password_hash` via a
`SECURITY DEFINER` RPC (`verify_member_password`). This means Postgres RLS can only ever gate by
the broad `anon`/`authenticated` role — it has no way to know "is this really user X," so almost
every table's RLS policy is `USING (true)` for both roles. That's not an oversight in most cases;
it's this app's whole architecture.

Layered on top of that base:
- **Member password** (`profiles.password_hash`) — first login prompts setup, now gated behind an
  email OTP (`request_account_setup_otp`/`verify_account_setup_otp`) so knowing someone's ID+email
  (both somewhat guessable) isn't enough to hijack their account before they ever log in.
- **Admin console password** (`profiles.admin_password_hash`) — separate from the member password,
  checked via `verify_admin_password` in `Login.tsx`'s `enterAdminConsole`. Success issues an
  **admin session token** (`issue_admin_session_token`/`verify_admin_session_token`,
  30-day expiry to match "keep me logged in," stored as `user.adminToken` in the router's user
  object and inside the `chorale_session` blob in local/sessionStorage).
- **HR incident-report password + emailed OTP** — a *third*, separate credential
  (`hr_incident_access` table, singleton row), gating `AdminIncidents.tsx`. Success issues an
  **HR session token** (`issue_hr_session_token`/`verify_hr_session_token`, 4h expiry, kept in
  `sessionStorage` under `hr_incident_session_token` — deliberately separate from the router's user
  object since it should die with the browser tab, not persist like the admin session does).

**The critical thing this enables**: several tables hold data sensitive enough that "anyone with
the public anon key" (extractable from any deployed bundle — not a secret) being able to read or
write it is unacceptable. Those go through a service-role-backed Edge Function or a
`SECURITY DEFINER` RPC that verifies one of the session tokens above, instead of relying on RLS
alone:
- `incident_reports`/`incident_report_comments` — no client-readable RLS at all. All reads/writes
  for HR go through the `hr-incident-reports` Edge Function; a member reading their own past
  reports goes through `member-incident-reports` (honest caveat: that endpoint trusts whatever
  `account_id_fk` the client sends, since there's no real per-request identity to check it
  against — it's still a huge improvement over the old world where the whole table was
  `SELECT`-able by anyone).
- `incident-evidence` and `payment-proofs` storage buckets — private, served only via short-lived
  signed URLs (`get_evidence_url` action in `hr-incident-reports`; `admin-payment-proofs` Edge
  Function) instead of the public-bucket URLs they used to be.
- `profiles.is_admin`, `password_hash`, `admin_password_hash`, `security_answer_hash_*`, and every
  session-token/OTP column — column-level `REVOKE UPDATE`/`REVOKE INSERT` for `anon`/`authenticated`
  (see `20260841_lock_down_credential_and_admin_columns.sql`). **This is load-bearing**: without
  it, literally every credential system above is just UI theater, since anyone could set
  `is_admin = true` on themselves with one direct REST call. If you ever add a new sensitive column
  to `profiles`, it needs the same REVOKE, and a `SECURITY DEFINER` RPC as the only legitimate
  write path.
- `fee_records.status` can't be set to `'paid'` directly (`WITH CHECK (status <> 'paid')`) — only
  `admin_approve_payment`/`admin_reject_payment` (admin-token-gated) can. Members can still write
  their own payment submission fields (`status -> 'pending'`, sender/receiver account info, etc.).
- `excuse_requests.status`/`approved_by`/`admin_response` are revoked from direct writes —
  `admin_decide_excuse` (admin-token-gated) is the only path. Members can still edit their own
  pending request's content (date/type/reason/etc).

**What's still open** (`USING (true)`, no extra gate) because the blast radius is lower: `events`,
`excuse_requests` content fields, `fee_rules`, `announcements`, `music_categories`/`music_items`,
`rules_documents`, `org_settings`. A few of these also allow `DELETE` for anon/authenticated
(events, music_items, rules_documents) — someone could vandalize the calendar/library/rules page
via a raw REST call. Known, not yet addressed; ask before doing a sweep across these, it's the
same shape of fix as the tables above (RPC + revoke) but touches a lot of surface area.

**If you're asked to add a new feature that touches sensitive data**: default to assuming the
table has no real protection beyond role-level RLS, and ask whether it needs the Edge-Function/RPC
treatment before shipping something in that flat `USING (true)` shape.

## Session/token pattern (reuse this, don't reinvent it)

Every credential above follows the same shape — copy it rather than designing something new:
1. Password check via a `SECURITY DEFINER` RPC returning `NULL` (no password set yet) /
   `true` / `false`.
2. On success, issue a session token: `encode(gen_random_bytes(24), 'hex')`, store only
   `crypt(token, gen_salt('bf', 10))` + an expiry column, return the plain token once.
3. Client holds the plain token (React state / sessionStorage / the router's user object,
   depending on how long it should live) and sends it as a body field to whatever Edge
   Function or RPC needs to prove the caller is legitimately authenticated.
4. The Edge Function/RPC calls `verify_*_session_token(token)` first, using the service-role
   client (Edge Functions) or running as `SECURITY DEFINER` (RPCs) to legitimately bypass RLS
   only after that check passes.
5. Rate-limit both the password check and any OTP verification — see
   `20260837_rate_limit_password_and_otp.sql` for the exact shape (5 attempts / 2h lockout for
   passwords, 5 wrong guesses invalidates an OTP code forcing a fresh one).

## Conventions actually used in this codebase

- **Styling**: inline `style={{}}` objects, reading colors/fonts from `useTheme()` (returns
  `theme.*`) and `FONTS` (from `theme.ts`). No Tailwind, no CSS modules, no styled-components.
  Dark mode exists (`theme.mode`) — a recurring bug pattern this session was using a *fill* color
  (`theme.greenDark`) as *text* color, breaking contrast in dark mode; when adding new UI, sanity
  check text colors against both themes.
- **Components**: PascalCase files in `src/app/components/ui/` (Card, Button, Icon, PageHeader,
  Chip, Avatar, etc.) are the real, hand-built shared components — reuse these, don't reach for a
  UI library.
- **Screens**: one file per route in `src/app/components/screens/`, named `Admin*`/`Member*`
  matching the `Route` union in `App.tsx`. `Shell.tsx` (in `components/layout/`) is the sidebar +
  topbar chrome wrapping every logged-in screen.
- **Data loading**: `src/app/data.ts` exports mutable `let` bindings (`MEMBERS`, `EVENTS`,
  `EXCUSE_REQUESTS`, etc.) that `initializePublicData()`/`initializeUserData()` overwrite with real
  Supabase data before/after login. Only `EVENTS` and `FEE_RECORDS` keep a single hardcoded
  fallback sample (shown only if the real table is empty) — everything else starts empty and stays
  empty on a genuinely empty result. Don't reintroduce a `.length > 0` fallback-to-mock check
  elsewhere; it silently hides real empty states behind fake data (this was a real bug fixed this
  session across six tables).
- **Viewport/responsive**: `useViewportWidth()` (`src/app/utils/useViewportWidth.ts`) is the one
  shared resize hook — don't re-implement it inline (it was copy-pasted into 16 files before being
  consolidated).
- **Toasts**: `useApp().showToast(msg, tone?)`.
- **Router state**: `useRouter()` → `{ route, role, user, previousRoute, go }`. `user` carries
  whatever was in the login payload, including `adminToken` for admins — don't assume it only has
  `id`/`name`/`email`.

## Edge Functions (`supabase/functions/`)

| Function | Purpose | Gate |
|---|---|---|
| `send-email` | Proxies Resend so the API key stays server-side | none (called by any client feature that sends email) |
| `weekly-digest`, `event-reminders` | Scheduled via `pg_cron` | none (server-triggered) |
| `hr-incident-reports` | All HR reads/writes on incident reports + evidence signed URLs | HR session token |
| `member-incident-reports` | A member's own past incident reports | trusts client-supplied `account_id_fk` (documented limitation, see Auth model) |
| `admin-payment-proofs` | Signed URL for a payment-proof image | admin session token |

Deploy with `supabase functions deploy <name>` — same manual-step caveat as migrations.

## Known gaps / good next steps

- **No real per-request identity.** Every mitigation above is working around this, not fixing it.
  The actual fix is migrating to Supabase Auth (or some other real session mechanism) so RLS can
  finally scope by "this specific user," not just role. Large lift, hasn't been started.
- **`events`/`music_items`/`rules_documents` still allow anon `DELETE`.** Same fix shape as the
  tables already locked down; not yet done, ask before doing a sweep.
- **No route-based code splitting.** `pnpm build` currently produces one ~817 KB JS chunk serving
  both member and admin screens to everyone. Lazy-loading (`React.lazy`) admin-only screens (or
  splitting by role generally) would cut initial load meaningfully.
- **Choir photo assets are huge** (`src/imports/*.png`, several 500 KB–2 MB each, unresized/
  uncompressed). Converting to WebP and sizing to actual display dimensions would be a large,
  low-risk win — no tooling for this in the current toolchain, needs to be done externally and the
  files swapped in.
- **Payment-proof/incident-evidence buckets became private this session** — if you're testing
  locally against an older Supabase project, make sure the corresponding migrations have actually
  been run (see Migrations above); a stale bucket state will make image display silently fail.

## Things not to do

- Don't add Tailwind classes, shadcn/ui components, or any new UI library — this codebase
  deliberately doesn't use one.
- Don't hardcode API keys/secrets in source files, ever — Resend and Supabase service-role keys
  live only in Edge Function secrets.
- Don't assume a migration has been run just because the file exists in the repo — always tell the
  user which ones need running.
- Don't add a new sensitive-data table/column with a blanket `USING (true)` policy without at
  least flagging it — see Auth model above for why that's a real, previously-exploited-in-review
  vulnerability class in this specific app, not theoretical.
